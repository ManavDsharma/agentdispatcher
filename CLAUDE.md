# Project: Agentic Support Portal

## What this is

A support-ops web app, conceptually similar to an L1-assistant we've built before, but standalone. This phase covers the **frontend + a real FastAPI backend reading tickets from DynamoDB**, **real Cognito-backed sign-in with an admin-approval access flow**, and **a live AI Agent chat** wired to `dtp_agent` (see Pages).

**Two separate backends, don't confuse them:** (1) the FastAPI app in `backend/` (tickets, reference data, agent bridge) at `VITE_API_BASE_URL` (default `http://localhost:8001`); (2) a **separate Auth API that is not in this repo** at `VITE_AUTH_API_BASE_URL` (Cognito-backed: `/auth/*`, `/admin/*`). The frontend talks to both; `backend/` itself has no auth code.

**Architecture pivot (superseded an earlier ServiceNow-ingestion design):** we originally had the backend call the ServiceNow Table API directly (and, briefly, a fuller connector/sync-service layer that ingested ServiceNow into DynamoDB from our own backend). Both are gone. **DynamoDB is now the sole source of truth, populated by something outside this codebase** — we don't sync, poll, or ingest anything here. The backend only reads from DynamoDB (with a mock-data fallback) and writes back a small editable-field set for tickets we own. `app/connectors/`, `app/mapping/`, and `app/services/sync_service.py` no longer exist. (`app/integrations/` **does** exist again, but only for the AI agent clients — nothing ITSM-related.) `Settings` still declares unused `SERVICENOW_INSTANCE_URL/USERNAME/PASSWORD` fields left over from the old design; nothing reads them and they can be deleted.

What _is_ built here is the connection to it: `WS /ws/agent` (browser↔backend) plus real `local`/`agentcore` client adapters (backend↔dtp_agent), config-switchable, with a canned-response fallback. ### Roster upload (AI Agent chat → DynamoDB roster table)

A paperclip button next to the chat input accepts **`.xlsx` or `.csv` only** (5 MB, 5000 data rows max) and loads a monthly roster into the roster table (`ROSTER_TABLE_NAME`). **The backend does the parsing, validation and write — not `dtp_agent`** (separate repo; and bulk writes shouldn't depend on an LLM). The upload goes over plain HTTP, not the agent WebSocket, and the agent isn't told about it yet. Flow has three user actions so nothing happens without an explicit click: **(0) attach** — choosing a file with the paperclip only shows it as a chip above the input (name, size, ✕ to remove; client-side type/size problems show inline there); nothing is sent. **(1) Send** (button or Enter) uploads and validates it — if text is also typed, the file goes first and the text is sent to the agent as a normal message. **(2) Confirm** on the result card writes it:

1. `POST /api/roster/uploads` (multipart: `file`, `uploaded_by`) validates and **writes nothing**. Returns an `upload_id` plus a report that the chat renders as `components/agent/RosterUploadCard.jsx`: how each column was read, errors by row/column, warnings, a 5-row preview, team/employee/period summary.
2. `POST /api/roster/uploads/{id}/commit` — only offered when there are zero errors — writes the rows staged in step 1. The staged rows live **server-side in memory (30-min TTL)**, so the browser can't alter what was validated; a restart means "attach the file again". Single uvicorn worker assumed.

- **Agreed sheet (17 columns):** Team ID, Team Name, Team Email ID, Emp ID, Employee Name, Employee Email, Year, Month, Days_Availability, Level, Shift, Shift Start Time, Shift End Time, Active, Created On, Updated On, Updated By. One row = one employee for one month. **Required:** Team ID, Emp ID, Employee Name, Year, Month — a missing required column blocks the upload; any other missing column is a warning and is stored blank.
- **Smart header matching** (`app/domain/roster_schema.py::match_headers`), three passes where a surer match always beats a looser one: (1) exact ignoring case/spaces/underscores/punctuation (`emp_id`, `DAYS AVAILABILITY`); (2) known aliases (`Employee ID` → Emp ID, `Shift Start` → Shift Start Time, …); (3) close misspellings (similarity ≥ 0.85 and clearly ahead of the runner-up) — these are accepted but flagged **"Assumed — check"** in the card. Unrecognised headers are ignored and listed. The header row is found automatically within the first 15 rows (title rows above it are fine) and, for `.xlsx`, the first visible sheet that has one is used.
- **Row rules:** Year 2000–2100; Month 1–12 or a month name/abbreviation; emails format-checked (Team Email may list several separated by `;`/`,`); shift times parsed (`9:00`, `9 AM`, Excel time cells) and stored as `HH:MM`; Active normalised to `"Yes"`/`"No"` (blank → `"Yes"`, matching the real table's string values; anything else is an error); duplicate team+employee+year+month inside the file is an error. **All-or-nothing:** any error blocks the whole upload. **Days_Availability is a JSON object of day → Y/N** (`{"1": "Y", "2": "N", …}`, matching the real data): it must parse, keys must be days 1–31, values Y/N (case-insensitive, normalised to upper case) and it's re-saved in the same `{"1": "Y", "2": "N"}` layout; up to 2000 characters (every other field is capped at 200). A day count that doesn't match the month (e.g. 30 entries for a 31-day August) is only a **warning**, since real files do this. Other values are trimmed, not reinterpreted — **Year/Month/Level/Shift are stored as the text in the file** (e.g. Month `8`, Shift `S1`), which matches the sample sheet; confirm against the existing table's rows.
- **Write shape:** one item per row with a **random-UUID `UID`** (chosen deliberately), `emp_id` mirrored into `employee_id` (the table carries both), all sheet fields in snake_case, plus `employee_email` (new — not in the table's documented schema; DynamoDB is schemaless). `created_on` keeps the file's value or is set to now; `updated_on` is always now; `updated_by` is the signed-in user's email (sent by the frontend from `useAuth()` — **unverified until the backend validates tokens**), else the file's value, else `roster-upload`.
- **Duplicates / retries:** because UIDs are random, uploading the same month twice **adds a second set of rows** — it never updates or removes existing ones. To soften that, validation scans the table and warns "N row(s) already exist for the same team, employee and month". UIDs are assigned at validation time, so **retrying a failed commit is safe** (same UIDs overwrite, no duplicates) and committing an already-committed upload just returns the earlier result.
- **Mock fallback:** if `ROSTER_TABLE_NAME` is unset the commit goes to an in-memory mock roster (`mock_reference_data.add_mock_roster_rows`) and the card says so in amber — it is **not** persisted. Unlike tickets/reference reads, a *failed real* DynamoDB write is **not** swapped for the mock; it returns 502 with how many rows were written.
- **Layering:** `routes/roster.py` → `services/roster_upload_service.py` (orchestration, staging) → `services/roster_file_reader.py` (xlsx/csv → text rows; checks real content, not just the extension) and `domain/roster_schema.py` (pure matching/validation) → `store/roster_repository.py` (paginated scan, chunked `batch_writer`, mock fallback).
- **New dependencies** (both in `requirements.txt`): `python-multipart` (FastAPI form uploads) and `openpyxl` (read `.xlsx`).
- **Not browser-tested yet:** backend verified over HTTP against the mock path (headers/aliases/typos, title rows, CSV `;`/cp1252, bad values, fake/oversize/renamed files, double commit); the frontend card compiles, lints and builds, but wasn't exercised in a browser because sign-in needs the external Auth API. **Don't test uploads against the real roster table** (see the priority-matrix incident above) — leave `ROSTER_TABLE_NAME` unset to use the mock path.

## Known backend gaps (deferred on purpose — to be fixed later)

- **No server-side auth** on any FastAPI route or the WebSocket (see "Auth & access control"); roles other than admin aren't enforced; the signed-in user isn't passed to the agent; nothing refreshes expired tokens.
- **`backend/venv` is Python 3.9.1, but the existing code needs 3.10+** — `agent_service.py` / `agent_client_*.py` use `str | None` annotations, so `import app.main` raises `TypeError` under that venv. Run the backend on Python 3.10+ (3.10, 3.11 and 3.12 are installed on this machine) and rebuild the venv. The new roster code is written to also work on 3.9.
- Unused `agent_client_agentcore1.py` duplicate and leftover `SERVICENOW_*` settings (see above).
- Reference-data reads (`reference_repository`) use a single un-paginated `scan()`, so tables over 1 MB would be silently truncated; the roster upload's own scan is paginated.

## Auth & access control

Cognito-backed, via a **separate Auth API (outside this repo)**. Frontend contract only — `services/authService.js` (public) and `services/adminService.js` (Bearer-authenticated), both reading `VITE_AUTH_API_BASE_URL` and throwing `"VITE_AUTH_API_BASE_URL is not configured."` if unset. Errors surface `response.message`.

- **Endpoints used:** `POST /auth/register`, `/auth/login`, `/auth/new-password`, `/auth/refresh`, `/auth/password-reset/request`, `/auth/password-reset/confirm`; `GET /admin/users`, `POST /admin/users/action` (`{email, action}` with `APPROVE | REJECT | RESET_APPROVE | RESET_REJECT`).
- **Onboarding flow (no self-serve accounts):** Register is an **access request** — first name, last name, email, access type (`Admin | L1 | L2 | Operate Lead`) → an admin approves in Admin Control → the user is emailed a temporary password → first login returns challenge `NEW_PASSWORD_REQUIRED` → `LoginPage` switches in place to a "Create your password" form (min 8 chars, must match) → `completeNewPassword` signs them in.
- **Password reset flow:** `ForgotPasswordPage` is a 4-step machine (`request` → `waiting` → `confirm` → `complete`). Requesting a reset goes to admin approval; once approved the user gets a verification code and submits email + code + new password (min 8, must match). The page doesn't auto-advance from `waiting` to `confirm` — the user clicks "I have received my reset code".
- **Session (`context/AuthContext.jsx`):** `{accessToken, idToken, refreshToken, expiresIn, user}` held in React state and mirrored to **`sessionStorage` under `l1d_auth_session`** (cleared on tab close; the key is exported as `SESSION_KEY` and also hard-coded in `apiClient.js` — keep in sync). Exposes `login`, `completeNewPassword`, `refresh` (uses `refreshToken` + `user.email`; logs out on failure), `logout`, `user`, `isAuthenticated` (= has `accessToken`) and `isAdmin`. **Nothing calls `refresh()` automatically yet** — there's no expiry timer or 401 interceptor, so an expired access token just starts failing requests until the user signs out/in.
- **Roles:** `user.cognitoGroup` — `DTP_OPERATE_AGENT_ADMIN` / `_L1` / `_L2` / `_OPERATE_LEAD`. **Only the admin group is enforced** (`isAdmin` → Admin Control nav + `AdminRoute`); L1/L2/Operate Lead are display labels only (Sidebar user card, Settings) and don't change what a user can do in Tickets or the AI Agent.
- **Routing (`App.jsx`):** `GuestRoute` (`/login`, `/register`, `/forgot-password`; signed-in users bounce to `/`) → `ProtectedRoute` (everything else, bounces to `/login`) → `AppShell` (Sidebar + `Outlet`) → `AdminRoute` (`/admin-control`, non-admins bounce to `/`). Login success navigates to `/`.
- **Frontend-only enforcement — important:** `apiClient.js` attaches `Authorization: Bearer <accessToken>` to every FastAPI call, but **`backend/` does not validate it** (no JWT/Cognito verification, no `Depends` auth anywhere). `/api/tickets`, `/api/reference/*`, `/api/agent/*` and `/ws/agent` are effectively open to anyone who can reach the server, and the 403/`isAdmin` checks live in the browser (the Auth API presumably enforces `/admin/*` itself, but that's outside this repo). Treat route guards as UX, not security, until the FastAPI backend verifies Cognito tokens.

## Ticket data (DynamoDB, in scope this phase)

DynamoDB is the sole source of truth for tickets. We don't ingest, sync, or poll any ITSM tool from this codebase — whatever's in the table is what the UI shows. Real DynamoDB table schema (PK `ticket_id`):

```
ticket_id, assigned_to, assignment_duration, assignment_sla, category, closed_at, created_at,
description, has_assignment_sla_breach, has_resolution_sla_breach, opened_by, opened_for,
priority, resolution_duration, resolution_sla, short_description, source_system, state,
sub_category, team_id, updated_at, urgency, url, working_notes
```

- `GET /api/tickets` / `GET /api/tickets/{ticket_id}` read directly from DynamoDB via `app/store/ticket_repository.py`. `PATCH /api/tickets/{ticket_id}` is a **real write-through to DynamoDB** (`update_item`, not a local-only change). `updated_at` is always bumped server-side to "now" on any successful patch. Enforced server-side in `ticket_service.update_ticket` (403 on an `external_redirect` ticket, 400 on an unknown field), not just hidden in the UI.
- **Editable set, current (`app/domain/ticket.py::EDITABLE_FIELDS`):** `short_description, description, category, sub_category, urgency, impact, state, assigned_to, opened_by, opened_for, team_id, working_notes`. Explicitly **not** editable: `ticket_id` (PK), `created_at`/`updated_at`/`closed_at` (backend-owned), `source_system`/`url` (hidden from the edit form entirely — they drive `management_mode`, not user-facing), `priority` (derived, see below), and the SLA/duration/breach fields (display-only, so an L2 edit can't fake SLA compliance).
- **`impact` is a new field, not in the original real schema** — added because Priority needs it. Existing real tickets show it blank until edited (pydantic default `""`); nothing breaks reading items that don't have the attribute at all.
- **Priority is derived, not directly editable:** `app/domain/priority_matrix.py::compute_priority(impact, urgency)` implements the standard ServiceNow default 3×3 matrix (High/Medium/Low × High/Medium/Low → `"1 - Critical"` … `"5 - Planning"`). `ticket_service.update_ticket` recomputes and overwrites `priority` server-side whenever `impact` or `urgency` is part of the patch — the client can never set `priority` directly (not in `TicketPatch`/`EDITABLE_FIELDS`). The frontend (`utils/priorityMatrix.js`) mirrors the same table for an instant preview in the drawer, but the backend's copy is authoritative. Note: existing real priorities use ServiceNow's own format (e.g. `"P4-Low"`); once impact/urgency are edited, the format changes to the matrix's `"4 - Low"` style — a known cosmetic inconsistency between untouched and edited tickets, not a bug.
- **Cascading dropdowns, backed by two new real reference tables** (categorization matrix + roster — see next bullet): the drawer's Category/Sub-category/Team ID/Assigned-to fields are `<select>`s whose _options_ narrow as you go — Category filters Sub-category options to matching matrix rows; Category+Sub-category filters Team ID options; Team ID filters Assigned-to options to that team's roster. **Changing an upstream field resets every downstream field to an explicit "Choose below" placeholder (`""`) rather than auto-picking the first option** (`TicketDetailDrawer.jsx::handleCategoryChange`/`handleSubCategoryChange`/`handleTeamIdChange`) — deliberate: auto-selecting looked like a system recommendation it wasn't. `handleSave` refuses to submit while sub-category/team/assignee are still unset, so a category change can't silently save blank fields if you forget to reselect them. Urgency/Impact/State are fixed-option dropdowns (High/Medium/Low; New/In Progress/On Hold/Resolved/Closed/Canceled — no `on_hold_reason` sub-field for now, deliberately skipped). Every dropdown's option list is still unioned with the ticket's _current_ value even if that value isn't in the reference data, so loading an existing ticket never silently discards a value it doesn't recognize.
- **New reference tables — real, not derived from ticket data:** `CATEGORIZATION_MATRIX_TABLE_NAME` (schema: `issue_id` PK, `category_name`, `sub_category_name`, `team_id`, `impact`, `urgency`, `issue`, `issue_type`, `active`, …) and `ROSTER_TABLE_NAME` (schema: `UID` PK, `employee_id`, `emp_id`, `employee_name`, `team_id`, `team_name`, `active`, …), both in `.env`/`.env.example`. Read-only endpoints `GET /api/reference/categorization-matrix` / `GET /api/reference/roster` (`app/routes/reference.py` → `reference_service.py` → `reference_repository.py`), same mock-fallback philosophy as the main Tickets table (`app/mock_reference_data.py`), filtered to `active` rows in the service layer. This **replaced** an earlier, simpler approach where the assignee dropdown was derived client-side from `assigned_to` values already seen across loaded tickets — that approach is gone now that real roster/matrix tables exist.
- **If dropdown values look wrong/unexpected (e.g. a category that isn't in your real table), check `source`/`reason` on the reference endpoints before assuming a bug** — `GET /api/reference/categorization-matrix` and `/roster` report `{source: "mock"|"dynamodb", reason: "not_configured"|"connection_error"|null}` exactly like the main Tickets endpoint. `CATEGORIZATION_MATRIX_TABLE_NAME`/`ROSTER_TABLE_NAME` being unset in `.env` is not itself a bug — it's the same intentional mock-fallback path as everywhere else in this app — but it does mean the dropdowns show `app/mock_reference_data.py`'s made-up categories (including "Schedule", which isn't in any real table), not your real categorization/roster data, until those two env vars are set. Confirmed real once set: 50 real categorization rows / 13 real categories, 28 real roster entries / 10 real teams.
- **The real tables' `active` field is the string `"Yes"`, not a boolean** — `reference_service._is_active()` originally only recognized `True`/`"true"`/`1`/`"1"`, which silently filtered out every real row (0 items returned, even though `source: dynamodb` with no error — a real bug, not the not-configured/mock case). Fixed to normalize case/whitespace against both truthy (`true`/`yes`/`y`/`1`/`active`) and falsy (`false`/`no`/`n`/`0`/`inactive`) string forms, defaulting to **shown** for anything unrecognized rather than silently hiding real reference data over a formatting mismatch.
- **`app/store/dynamo.py::get_table(table_name)` takes an explicit table name now** (was hardcoded to the Tickets table) — needed once a second and third table existed. `ticket_repository.py` has its own `_table()` wrapper passing `settings.dynamodb_table_name`.
- **Incident, for the record:** while testing the priority-matrix change against a real ticket, PATCHing `impact`/`urgency` back to "revert" it also silently recomputed and overwrote `priority` (since priority is now always server-derived whenever those fields are touched) — there is no API path to set `priority` back directly. Had to fix the real DynamoDB item with a one-off boto3 script outside the normal app code path. Lesson: don't test writes against real production tickets once derived/computed fields are involved — use the mock fallback path instead.
- **Redirect vs. edit rule — explicit source_system allowlist:** `app/domain/ticket.py::VALID_REDIRECT_SOURCE_SYSTEMS` is a case-insensitive set of recognized platform values; `source_system` in that set → `management_mode: "external_redirect"` (ticket ID links to `url` in a new tab, not editable through us); anything else → `"internal_edit"` (opens our drawer/form). Plain derived property on `TicketRecord`, not stored. Real table's `source_system` values turned out to be `Chatbot`/`Email`/`Phone`/`Self-Service Portal`/`ServiceNow Portal` — the ticket's **intake channel**, not "which platform" — and every row has a real ITSM `url` regardless of channel. We went through a couple of iterations on this: url-presence-based (redirects everything, since every row has a url) → explicit allowlist with exactly `"servicenow"` (matches nothing real, since the actual value is `"ServiceNow Portal"`) → current: allowlist includes both `"servicenow"` and `"servicenow portal"`, so the 68 real `ServiceNow Portal` tickets redirect and the other 427 (Chatbot/Email/Phone/Self-Service Portal) stay editable in our UI even though they also carry a url. Extend the set as more platforms are recognized.
- Credentials: `Settings` models `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` explicitly (read from `.env`, passed straight into the `boto3.resource()` call in `app/store/dynamo.py`) — **do not** rely on "boto3 picks .env vars up automatically," it doesn't: `pydantic-settings` parses `.env` into its own `Settings` object only, it never copies values into the real process environment, so anything not declared as a `Settings` field (like AWS creds used to be) is silently invisible to boto3's own credential chain. This was a real bug that caused every DynamoDB call to fail with `Unable to locate credentials` even with valid keys in `.env`. Leave both blank to fall back to boto3's own chain (shared `~/.aws/credentials` / instance role) instead. `AWS_REGION=` present-but-blank must not beat the default — handled via `Settings.resolved_aws_region`, not the raw field. **The default is now `ap-south-1`** (was `us-east-1`); the same region is used for the AgentCore client.
- **Fallback:** if `DYNAMODB_TABLE_NAME` is unset, or any DynamoDB call fails (including `update_item`, so edits don't silently 500 when AWS creds aren't available locally), fall back to an in-memory mock dataset (`app/mock_data.py`) so the app stays demoable. The mock store is mutable in-process, so edits made while running mock-only still stick until restart.
- **Loosely-typed fields:** `created_at`/`updated_at`/`closed_at`/the SLA & duration fields are modeled as plain strings, not parsed dates/numbers — we don't control their real format from whatever ingests the table, and over-fitting the schema caused a real bug once already (see git history). Display them as-is; use the `has_*_sla_breach` booleans for color coding rather than computing our own countdown.
- **Priority/status badge colors & filter options:** matched case-insensitively against known labels (frontend `Badge.jsx`) with a neutral fallback tone for anything unrecognized; the Tickets page's status-tab and priority-filter option lists are derived from whatever values are actually present in the loaded tickets (not hardcoded), for the same reason.

## Data layer conventions

- Frontend: keep API calls behind a thin service layer (`/src/services/ticketsService.js` etc.) — components should not call `fetch` directly.
- Backend: the route layer (`app/routes/tickets.py`) never talks to DynamoDB or boto3 directly — it only calls `app/services/ticket_service.py`, which calls `app/store/ticket_repository.py`, which is the only module that decides real-DynamoDB-vs-mock.

## Non-goals right now

- No server-side auth on the FastAPI backend (Cognito session is frontend-only here; token validation, role-based permissions beyond admin, automatic token refresh, and passing the signed-in user to the agent are all open follow-ups — see "Auth & access control")
- No real execution of reminder/escalate actions (display + mock confirmation only)
- No production deployment concerns
- `dtp_agent` isn't deployed to Bedrock AgentCore Runtime yet — `AGENT_MODE=local` is the default; the `agentcore` path is built and real (see `docs/AI_AGENT_INTEGRATION.md`) but unverifiable until an `AGENTCORE_RUNTIME_ARN` exists
